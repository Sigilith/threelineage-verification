# V1.1.0 Release Workstream — Autonomy Under Pressure

Status: DEVELOPMENT CANDIDATE — NOT A RELEASE RESULT

## Objective

Add a reproducible flagship scenario to the existing ThreeLineage Verification repository. The scenario demonstrates risk-proportional authority attenuation under deteriorating operating conditions, bounded delegation, fail-closed decisions, and evidence integrity.

The work extends the existing V1.0.0 repository. It does not replace or rewrite the historical V1.0.0 release evidence.

## Public-facing scenario

**Autonomy Under Pressure: when operating conditions deteriorate, does an automated system reduce its permitted authority before reaching a hard safety boundary?**

Use a synthetic, non-actuating operational-technology (OT) scenario. A simulated controller proposes setpoint adjustments while telemetry indicates increasing headroom pressure, sequence drift, uncertainty, or a hardware safety trip.

The demonstration must make the distinction between a proposed action, a governed decision, a permitted delta, and physical execution explicit.

## Existing implementation to exercise

- `core/sigilith.py`: deterministic autonomy-pressure evaluation and four verdicts.
- `core/identity.py`: signed delegation-chain verification and monotonic scope/alpha bounds.
- `core/transaction_authorization.py`: Guardian-side single-use permit consumption and replay rejection.
- `core/traceguard.py`: local SHA-256 hash-chained decision evidence.
- `adapters/ot/boundary.py`: protocol-labelled telemetry normalization and non-actuating proposal evaluation.

The OT adapter is explicitly non-actuating. It does not write to OPC-UA, DNP3, IEC-61850, a PLC, an RTU, a breaker, or any physical device. The release must not imply otherwise.

## Required scenario sequence

1. **Nominal conditions:** a valid, in-scope proposal receives the expected full permit where the engine's configured conditions support it.
2. **Rising pressure:** a destabilizing proposal receives a reduced alpha and a proportionally clamped delta.
3. **High pressure / converging drift:** the engine returns HOLD_ESCALATE and the permitted delta is zero.
4. **Hard perimeter or invalid telemetry:** the engine returns FAIL_CLOSED and the permitted delta is zero.
5. **Delegation cap:** a valid delegated authority with a lower alpha cap cannot be exceeded by the proposal.
6. **Delegation escalation attempt:** an invalid scope or alpha escalation is rejected by the delegation verifier.
7. **Replay attempt:** a consumed single-use permit cannot be consumed again.
8. **Evidence integrity:** a clean TraceGuard ledger reload verifies; a modified record is rejected.

Each scenario must assert both the governance verdict and the effective permitted delta. A green status label alone is not evidence.

## Acceptance criteria

- Add deterministic tests using fixed inputs; avoid wall-clock-dependent assertions.
- Assert exact verdict classes and numerical bounds, not merely that a function returned.
- Assert that every HOLD_ESCALATE and FAIL_CLOSED scenario yields zero permitted delta.
- Assert that delegated alpha never exceeds the verified chain cap.
- Assert that replay is rejected.
- Assert that ledger tampering is detected on reload.
- Keep all OT tests non-actuating and synthetic.
- Preserve existing V1.0.0 tests, package boundaries, historical logs, and evidence files.
- Run the complete existing release gate plus the new tests in CI.
- Rebuild the manifest and SHA-256 sidecar only after the final candidate contents are settled.
- Record the exact commit, commands, dependency/runtime versions, test counts, and workflow run URL in the release report.

## TraceGuard integrity boundary

The TraceGuard implementation included in this public verification candidate is a **local SHA-256 hash-chained ledger**. It validates sequence, links and record hashes and detects record modification when the historical chain is not coherently rewritten. By itself, it does not establish external immutability or protect against an attacker able to rewrite the complete ledger and all trusted state held on the same host.

ThreeLineage has also developed the separate **TICP-1 checkpoint-integrity protocol**. The recorded local implementation uses domain-separated SHA-256 checkpoint hashes, detached Ed25519 signatures, previous-checkpoint linkage, sequence continuity and support for external anchor receipts. The project record reports 18/18 local tests passing. That result is historical project evidence, not a test run in this repository or an independent assessment.

Local protocol tests do not, by themselves, prove resistance to a privileged host attacker. The TICP-1 work has not yet demonstrated deployment with an independently controlled signer, a live externally maintained rollback-resistant anchor, or integration into this V1.1.0 execution-verification path. Those remain deployment and integration requirements. Accordingly, this candidate makes no claim that the V1.1.0 TraceGuard ledger alone resists full host compromise.

## Explicit limitations

This scenario is a deterministic software test using synthetic telemetry. It is not a live OT integration, physical actuation test, safety case, IEC 62443 certification, penetration test, independent security assessment, or proof of safe operation in a real industrial process.

TICP-1 is separate protocol work; its local test record must not be represented as proof of independent anchoring, rollback resistance under full host compromise, or integration into this candidate.
